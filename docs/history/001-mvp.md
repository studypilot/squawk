## 0. Entscheidungen (Moritz, 2026-10-10)

- Eigenes Repo `studypilot/squawk`, erst privat, später Open Source. Lizenz MIT ab dem ersten Commit.
- Ein Docker-Image, Postgres, generisches OIDC. Bei uns Google mit Restriktion auf `@studypilot.app`;
  die Domain-Restriktion allein regelt den Zugang, keine Access-Liste.
- Stack: TypeScript, pnpm-Workspace. Server Hono + Drizzle. Inbox React + Vite. Overlay ohne
  Framework in Shadow DOM. CLI als npm-Paket, global installiert. Kein MCP.
- Login im Overlay und in der CLI per Gerätecode-Flow. Agent-Tokens entstehen in der Inbox oder per
  CLI mit persönlichem Login, gelten global, optional auf eine Site beschränkt, sind widerrufbar.
- Screenshots sind Pflicht. Chrome-Extension (Manifest V3) für echte Viewport-Screenshots, verteilt
  als Zip aus GitHub-Releases. Ohne Extension DOM-Rendering als Fallback mit Hinweis. Ablage auf
  einem Filesystem-Volume.
- Status nur `open` / `resolved`. UI-Sprache Englisch. Live-Updates per Polling.
- GitHub-PR-Kommentare, Discord, nginx-Injection, netbird-expose-Option, Capacitor- und
  Electron-Screenshot-Adapter, Firefox, Ganzseiten-Screenshots: nicht im MVP.
- kube-Deployment im Plan, nur eine Prod-Instanz `squawk.studypilot.app`.
- Renderer-Einbindung als eigener Abschnitt (§12), Umsetzung nach dem ersten Release. Build-Flag für
  Runway-Dev-Bundles und den lokalen Vite-Dev-Server. Seitenschlüssel = Route + Parameter.

## 1. Ziel

Jede Person im Team kann auf einem beliebigen Teststand (Sandbox-Bundle auf dem iPad, lokal
exponierte Seite, Vite-Dev-Server, statisches HTML) eine Stelle anklicken, einen Screenshot
anhängen und einen Kommentar hinterlassen. Der Coding-Agent, der den Stand gebaut hat, liest die
offenen Squawks per CLI, antwortet und markiert sie als erledigt. Alles läuft über einen Dienst
mit einer Inbox.

Nicht-Ziele im MVP: siehe §0. Außerdem keine Mandantenfähigkeit (eine Instanz = eine Organisation),
keine externen Gäste, keine Realtime-Verbindung, kein Rich-Text.

## 2. Begriffe

| Begriff | Bedeutung                                                                                                                                                                                |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Site    | Sammelbecken für Squawks, Schlüssel ist ein String. Default: Hostname der Seite. Überschreibbar per `data-site`, bei uns meist der Branch-Name. Entsteht automatisch beim ersten Squawk. |
| Page    | Seitenschlüssel innerhalb einer Site. Default: `location.pathname + location.hash`. Überschreibbar per `Squawk.setPage()`.                                                               |
| Squawk  | Ein Thread: Anker, Screenshot, erster Kommentar, Status, Metadaten.                                                                                                                      |
| Comment | Antwort in einem Squawk. Autor ist ein Mensch oder ein Token.                                                                                                                            |
| Anchor  | Bündel aus Selektoren und relativer Position, mit dem der Pin wiedergefunden wird.                                                                                                       |
| Token   | Opaker Bearer-Token für Agents, gehasht gespeichert, mit Name, Ablauf, optionaler Site.                                                                                                  |

## 3. Architektur

```
                 ┌──────────────────────────────────────────┐
  squawk.js ────▶│  squawk-server (Hono)                     │◀──── squawk CLI (Agent, Token)
  (Overlay,      │  /api/*          JSON, Bearer oder Cookie │
   Bearer-Token) │  /auth/*         OIDC + Gerätecode        │◀──── Inbox (React, Cookie)
                 │  /squawk.js      Overlay-Script           │
  Extension ──▶  │  /               Inbox (statisch)         │
  (nur im Tab,   │  Postgres (Drizzle)   Volume /data        │
   kein Netz)    └──────────────────────────────────────────┘
```

- Ein Prozess, ein Image, ein Hostname. Server liefert Inbox und Overlay-Script selbst aus, damit
  Cookie und Script same-origin sind.
- Das Overlay spricht ausschließlich per Bearer-Token mit `/api`, nie per Cookie. Dadurch ist CORS
  trivial: `Access-Control-Allow-Origin` spiegelt den anfragenden Origin, keine Credentials.
- Die Extension redet nie mit dem Server. Sie liefert dem Overlay auf Anfrage einen Screenshot des
  Tabs. Auth und Upload bleiben im Overlay.
- Die CLI nutzt dieselbe `/api` wie das Overlay.

## 5. Datenmodell (Postgres, Drizzle)

```
users         id uuid, email unique, name, avatar_url, created_at, last_login_at
sites         id uuid, key unique, display_name null, created_at
squawks       id uuid, site_id, page text, number int (pro Site fortlaufend, für "#12"),
              status open|resolved, anchor jsonb, screenshot_id null, meta jsonb,
              created_by_user null, created_by_token null, created_at, resolved_at null,
              resolved_by_user null, resolved_by_token null
comments      id uuid, squawk_id, body text, created_by_user null, created_by_token null,
              created_at
screenshots   id uuid, squawk_id, path text (relativ zu /data), width, height,
              device_pixel_ratio, source extension|dom, created_at
tokens        id uuid, name, prefix text (erste 8 Zeichen, für die Anzeige), hash text unique,
              site_id null, created_by_user, created_at, expires_at null, revoked_at null,
              last_used_at null
device_codes  id uuid, device_code hash unique, user_code text unique (8 Zeichen, z. B. "WXYZ-1234"),
              kind overlay|cli, origin text null, status pending|approved|denied|expired,
              user_id null, token_id null, expires_at (10 min), created_at
```

- `anchor` ist §7.2. `meta` enthält `url`, `title`, `userAgent`, `viewport`, `devicePixelRatio`,
  `ref` (Branch oder Commit, frei vom Einbinder gesetzt) und `appVersion`, falls geliefert.
- Der erste Kommentar eines Squawks ist eine normale Zeile in `comments`. Die Liste zeigt ihn als
  Text des Squawks.
- Jede Tabelle hat `created_by_user` oder `created_by_token`, genau eins davon. Die UI zeigt bei
  Token-Autoren den Token-Namen mit Roboter-Symbol.
- Sessions werden nicht gespeichert: Cookie ist ein HS256-JWT mit `{sub, email}`, 12 h, wie bei
  Runway.
- Overlay- und CLI-Logins erzeugen Zeilen in `tokens` mit `name = "Overlay <origin>"` bzw.
  `"CLI <hostname>"`, 30 Tage Ablauf. Dadurch gibt es nur einen Token-Typ, und alle sind in der
  Inbox sichtbar und widerrufbar. Agent-Tokens unterscheiden sich nur dadurch, dass ein Mensch sie
  mit Namen anlegt.

## 6. Auth

### 6.1 OIDC für Menschen (Inbox)

- Generisch über `openid-client`: `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`,
  `OIDC_ALLOWED_EMAIL_DOMAINS` (kommagetrennt), optional `OIDC_HOSTED_DOMAIN` (setzt `hd` im
  Request und prüft den Claim, Google-spezifisch).
- Flow wie Runway: `GET /auth/login` legt `state` + PKCE in ein kurzlebiges Cookie und leitet zum
  Issuer. `GET /auth/callback` prüft E-Mail-Domain und `hd`, legt den User an oder aktualisiert
  ihn, setzt `squawk_session` (httpOnly, SameSite Lax, Secure bei https). `POST /auth/logout`.
- Bei uns: neuer Google-OAuth-Client, Redirect-URI `https://squawk.studypilot.app/auth/callback`,
  `OIDC_HOSTED_DOMAIN=studypilot.app`. Moritz legt den Client an.

### 6.2 Gerätecode für Overlay und CLI

Angelehnt an RFC 8628, ohne Client-Registrierung.

1. Client: `POST /api/auth/device` mit `{kind, origin?}` → `{deviceCode, userCode,
verificationUrl, expiresIn, interval}`. `verificationUrl` ist `https://<server>/device?code=WXYZ-1234`.
2. Overlay zeigt Code und Link als Schaltfläche, die einen neuen Tab öffnet. CLI druckt Code und
   Link und öffnet den Browser, falls möglich.
3. Mensch landet auf `/device`, meldet sich notfalls per OIDC an, sieht Code, Art (Overlay auf
   `origin` oder CLI auf `hostname`) und bestätigt.
4. Client pollt `POST /api/auth/device/token` mit `deviceCode` alle `interval` Sekunden → bei
   `approved` ein Token `sqk_<32 zufällige Zeichen>`, der sofort in `tokens` gehasht liegt.
5. Overlay speichert den Token in `localStorage` des Seiten-Origins unter `squawk:<server>:token`.
   CLI speichert ihn in `~/.config/squawk/config.json` (Mode 0600).

Rate-Limits: 5 Gerätecodes pro Origin und Minute, Polling höchstens einmal pro `interval`.

### 6.3 Autorisierung

- Eine Middleware akzeptiert für `/api` entweder `Authorization: Bearer sqk_…` (Hash-Lookup,
  Ablauf und Widerruf prüfen, `last_used_at` nachführen) oder das Session-Cookie. Die Inbox nutzt
  das Cookie, alles andere Bearer.
- Jeder Authentifizierte darf alles lesen und schreiben. Site-beschränkte Tokens sehen nur ihre
  Site. Nur Menschen (Cookie oder Token mit `name` beginnend mit "Overlay"/"CLI" und `created_by_user`
  = der Mensch selbst) dürfen Tokens anlegen und widerrufen. Ein Agent-Token darf keine Tokens
  anlegen.
- Screenshots sind nur authentifiziert abrufbar. Die Inbox lädt sie per `<img>` same-origin mit
  Cookie, das Overlay per `fetch` mit Bearer und `blob:`-URL.

## 7. Overlay (`squawk.js`)

### 7.1 Einbindung und Konfiguration

```html
<script
   src="https://squawk.studypilot.app/squawk.js"
   data-site="feature/sketch/multipage"
   data-ref="186c6b6b3"
   defer
></script>
```

- Server-URL kommt aus `script.src`. `data-site` optional (Default Hostname). `data-ref` optional
  (landet in `meta.ref`). `data-page` optional, sonst Pfad + Hash.
- Globales Objekt `window.Squawk` mit `setPage(key)`, `setSite(key)`, `setMeta(partial)`,
  `open()`, `close()`, `capture()`. Alle Aufrufe sind auch vor dem Laden sicher, weil das Script eine
  Queue abarbeitet (Muster `window.Squawk = window.Squawk || {q: []}` wie bei Analytics-Snippets).
- Seitenwechsel: `pushState`/`replaceState` werden gepatcht, `popstate` und `hashchange` gehört.
  Der app-renderer schreibt seine Navigation bereits als `#path?{json}` in den Hash
  (`NavigationUrlState.serializeToUrl`), deshalb reicht dort der Default. Ein Aufruf von
  `setPage()` überschreibt den Default dauerhaft.
- Bundle-Ziel: unter 60 KB gzipped, keine Abhängigkeiten außer `@medv/finder` und einer
  DOM-zu-Bild-Bibliothek für den Fallback (`html-to-image` oder `modern-screenshot`, Entscheidung
  beim Bau nach Größe und Canvas-Verhalten).

### 7.2 Anker

Beim Klick auf ein Element werden gespeichert:

```jsonc
{
   "version": 1,
   "selectors": {
      "testId": "note-list-item-4711", // data-testid, data-test, id, falls vorhanden
      "css": "main > div:nth-child(2) > article", // @medv/finder, seedMinLength 4
      "xpath": "/html/body/div[1]/main/div[2]/article",
      "text": { "exact": "Hausaufgaben", "prefix": "…", "suffix": "…" } // innerText-Zitat, 32 Zeichen Kontext
   },
   "rect": { "x": 0.42, "y": 0.18 }, // Klickpunkt relativ zum Element (0..1)
   "page": { "x": 812, "y": 1240, "scrollX": 0, "scrollY": 880 }, // Fallback in Seitenkoordinaten
   "viewport": { "width": 1440, "height": 900 }
}
```

Wiederfinden in dieser Reihenfolge: `testId` → `css` → `xpath` → Textzitat über alle Elemente mit
passendem `innerText`. Jeder Treffer wird gegen den Text und die Größe plausibilisiert. Kein Treffer
→ Pin an `page`-Koordinaten mit Kennzeichen „orphaned“ und dem Screenshot als Referenz. Nach dem
ersten Render und bei DOM-Änderungen wird per `MutationObserver` mit Debounce 250 ms neu verankert.

Für `<canvas>`-Elemente (Sketch) ist der Anker das Canvas selbst plus `rect`. Dort entscheidet der
Screenshot.

### 7.3 Bedienung

- Schwebende Schaltfläche unten rechts, „schlafend“, Badge mit Anzahl offener Squawks der Seite.
- Klick oder Taste `c` → Pin-Modus: Cursor wird Fadenkreuz, gehovertes Element bekommt Rahmen,
  Klick setzt Pin, Overlay blendet sich aus, fordert Screenshot an (§8), blendet sich mit
  Kommentarfeld wieder ein. Escape bricht ab.
- Screenshot-Vorschau mit Pin-Marker. Kommentar, Senden. Erfolg zeigt den Squawk mit Nummer.
- Panel mit Liste: Squawks der aktuellen Seite zuerst, dann restliche der Site, Filter offen /
  erledigt. Klick auf einen Eintrag scrollt zum Pin und öffnet den Thread. Antworten, Erledigt,
  Wieder öffnen, Link kopieren (`<page-url>#squawk=<id>`, beim Laden mit diesem Fragment öffnet sich
  der Thread).
- Nicht angemeldet → Panel zeigt nur „Sign in“, der Gerätecode-Flow läuft im Panel.
- Polling alle 5 s, solange das Panel offen ist, sonst alle 60 s für das Badge.
- Alles in einem Shadow Root mit eigenem CSS, `z-index` maximal, `pointer-events` nur auf eigene
  Elemente. Fonts system-ui.
- Touch: Pin-Modus per Tipp auf die Schaltfläche, dann Tipp auf die Stelle. Ausreichend für das iPad
  im Browser; die WKWebView-Einbindung ist §12.

## 8. Extension (Chrome, Manifest V3)

- Bestandteile: `content.js` (in allen Tabs, `matches: <all_urls>`, läuft in der isolierten Welt),
  `background.js` (Service Worker), `popup` nur mit Status und Version.
- Berechtigungen: `activeTab`, `scripting` nicht nötig. `captureVisibleTab` braucht `activeTab`
  oder `<all_urls>`; da das Overlay den Screenshot ohne Klick auf das Extension-Icon braucht, ist
  `<all_urls>` nötig. Das ist bei Load-unpacked-Verteilung im Team akzeptabel und wird in der
  Doku genannt.
- Protokoll zwischen Overlay und Extension über `window.postMessage` mit Namespace `squawk-ext`:
   1. Overlay beim Start: `{type: "squawk-ext:ping"}` → Content-Script antwortet `pong` mit Version.
      Damit weiß das Overlay, ob echte Screenshots möglich sind, und zeigt das im Pin-Dialog an.
   2. Overlay: `{type: "squawk-ext:capture", requestId}` → Content-Script → Background →
      `chrome.tabs.captureVisibleTab(windowId, {format: "png"})` → Antwort `{type:
"squawk-ext:captured", requestId, dataUrl, devicePixelRatio}`.
   3. Vor der Anfrage versteckt das Overlay seine UI und wartet zwei Frames; danach wieder sichtbar.
- Der Screenshot wird im Overlay auf höchstens 2560 px Breite verkleinert, als PNG hochgeladen.
- Sicherheit: Das Content-Script beantwortet `capture` nur nach vorherigem `ping` aus demselben
  Dokument und nur, wenn der Nutzer gerade im Tab geklickt hat (`navigator.userActivation.isActive`).
  So kann eine beliebige Seite keine stillen Screenshots ziehen.
- Build mit Vite, Ausgabe `dist/extension`, Release-Zip `squawk-extension-<version>.zip`. Doku:
  `chrome://extensions` → Entwicklermodus → Entpackt laden.

Fallback ohne Extension: `html-to-image` auf `document.documentElement` mit Clip auf den Viewport,
Hinweis „Approximate screenshot. Install the Squawk extension for exact captures.“ `source = dom`.

## 9. Server-API

Alle Antworten JSON, Fehler als `{error: {code, message}}`. Prefix `/api`.

```
GET    /me                                → {user | token}
GET    /sites                             → [{key, displayName, openCount, resolvedCount, lastActivityAt}]
PATCH  /sites/:key                        → displayName
GET    /squawks?site=&page=&status=&cursor=&limit=
GET    /squawks/:id                       → Squawk mit Kommentaren und Screenshot-Metadaten
POST   /squawks                           multipart: json (site, page, anchor, meta, body), screenshot (png)
POST   /squawks/:id/comments              {body}
PATCH  /squawks/:id                       {status}
GET    /screenshots/:id                   PNG, Cache-Control private
GET    /tokens                            nur Menschen; eigene Tokens, Agent-Tokens aller
POST   /tokens                            {name, siteKey?, expiresInDays?} → Token im Klartext, einmalig
DELETE /tokens/:id                        Widerruf
POST   /auth/device, POST /auth/device/token   §6.2
```

- Body-Text ist Klartext mit minimalem Markdown (Absätze, `code`, Links werden erkannt). Rendering
  escaped immer; keine HTML-Eingabe.
- Grenzen: Body 10 000 Zeichen, Screenshot 8 MB, Anker 16 KB.
- CORS für `/api`: Origin spiegeln, Methoden GET/POST/PATCH/DELETE, Header Authorization +
  Content-Type, keine Credentials, Preflight-Cache 1 h.
- Statische Auslieferung: `/squawk.js` mit `Cache-Control: public, max-age=300` und ETag, Inbox
  unter `/` mit SPA-Fallback, Assets mit Hash und langer Cache-Zeit.
- Health: `GET /healthz` prüft DB und Schreibbarkeit von `/data`.

## 10. Inbox (React + Vite)

Routen:

- `/` Sites mit Zählern, sortiert nach letzter Aktivität.
- `/sites/:key` Liste, Filter Status (Default offen) und Seite (Dropdown aus vorhandenen Seiten),
  Suche im Text. Jede Zeile: Nummer, Vorschau des Screenshots, erster Kommentar gekürzt, Seite,
  Autor, Alter, Anzahl Antworten.
- `/squawks/:id` Screenshot groß mit Pin-Marker an `rect`-Position, Metadaten (URL als Link, Ref,
  Viewport, UA gekürzt), Thread, Antwortfeld, Erledigt-Schalter, Link „Open page“ mit
  `#squawk=<id>`.
- `/tokens` Eigene Tokens und Agent-Tokens: Name, Präfix, Site, Erstellt, Ablauf, zuletzt benutzt,
  Widerruf. Formular „Create agent token“ zeigt den Klartext einmalig mit Kopierknopf.
- `/device` Gerätecode bestätigen (§6.2).

Gestaltung bewusst schlicht: ein Stylesheet, System-Font, helles und dunkles Schema per
`prefers-color-scheme`. Keine Komponentenbibliothek.

## 11. CLI (`squawk`)

Installation: `npm i -g @studypilot/squawk-cli` aus GitHub Packages (`.npmrc` mit
`@studypilot:registry=https://npm.pkg.github.com`). Bei Veröffentlichung später npmjs.

Konfiguration: `~/.config/squawk/config.json` `{server, token}`. Umgebungsvariablen
`SQUAWK_SERVER` und `SQUAWK_TOKEN` überstimmen die Datei; so bekommen Agents ihr Token ohne Login.

```
squawk login [--server URL]            Gerätecode-Flow, speichert Token
squawk whoami
squawk sites [--json]
squawk list --site KEY [--status open|resolved|all] [--page KEY] [--json]
squawk show ID [--json]                 Thread, Metadaten, Anker, Screenshot-Pfad nach Download
squawk screenshot ID [--out PATH]       lädt das PNG (Default: ./squawk-<nr>.png)
squawk reply ID "text" | --file PATH | - (stdin)
squawk resolve ID [--comment "text"]
squawk reopen ID
squawk token create --name NAME [--site KEY] [--expires-days N]
squawk token list [--json]
squawk token revoke ID
```

- IDs akzeptieren die UUID oder `<site>#<nr>` bzw. nur `#<nr>` zusammen mit `--site`.
- `--json` gibt die API-Objekte unverändert aus. Exit-Codes: 0 ok, 1 Fehler, 2 nicht angemeldet.
- `squawk site-key` gibt einen Vorschlag für den Site-Schlüssel aus dem aktuellen Git-Branch aus
  (`git rev-parse --abbrev-ref HEAD`), damit Skill und Build-Flag denselben Default verwenden.

## 12. Claude-Skill

`skills/squawk/SKILL.md`, verlinkt nach `~/.claude/skills/squawk`. Inhalt:

- Trigger: „Squawks“, „Kommentare auf dem Teststand“, „was hat Jan angemerkt“, nach einem

- Ablauf: Site-Schlüssel bestimmen (Branch), `squawk list --site … --json`, pro Squawk

- Regeln: nie fremde Squawks ohne Fix schließen, Antworten kurz und konkret, Screenshot immer
  ansehen, Token nur aus `SQUAWK_TOKEN`.

## 13. Renderer-Einbindung (Monorepo, eigener PR nach dem ersten Release)

- Build-Flag `VITE_SQUAWK_SITE`. Ist es gesetzt, fügt ein kleines Vite-Plugin in
  `packages/app/renderer/vite.config.ts` per `transformIndexHtml` den Script-Tag mit `data-site`
  und `data-ref` (Commit-SHA aus `git rev-parse --short HEAD`) ein. Server-URL aus
  `VITE_SQUAWK_SERVER`, Default `https://squawk.studypilot.app`. Ohne Flag ändert sich nichts,
  Produktionsbuilds bleiben unberührt.
- `runway push` setzt `VITE_SQUAWK_SITE` automatisch auf den Branch-Namen, abschaltbar mit
  `--no-squawk`. Der lokale Vite-Dev-Server setzt es über `.env.local` oder die Kommandozeile.
- Seitenschlüssel: Der Hash enthält schon `path?{parameters}`. Damit der Schlüssel stabil und
  lesbar ist, ruft `NavigationController` nach jeder Navigation `window.Squawk?.setPage(path +
stabile Parameter)` auf; flüchtige Parameter (Scrollposition, Dialogzustände) bleiben außen vor.
  Die Liste der stabilen Parameter wird beim Bau entschieden.
- Capacitor: Das Script wird remote geladen; die App ist bei Sandbox-Tests online. Screenshots
  laufen dort über den DOM-Fallback, bis ein nativer Adapter kommt. Die Gerätecode-Anmeldung
  funktioniert in der WKWebView, weil kein Popup nötig ist; der Link öffnet Safari.

## 16. Sicherheit

- Tokens nur gehasht (SHA-256) in der DB, Klartext nur einmal in der Antwort. Präfix für Anzeige.
- Gerätecodes: 8 Zeichen aus einem 32er-Alphabet, 10 Minuten gültig, Bestätigung erfordert aktive
  Session, Codes werden nach Gebrauch gelöscht, Polling-Antworten unterscheiden nicht zwischen
  „unbekannt“ und „abgelaufen“.
- Inbox-Schreibzugriffe nur mit `Content-Type: application/json` und SameSite-Lax-Cookie; `/api`
  ohne Credentials-CORS. Damit ist CSRF abgedeckt, ohne Token-Mechanik.
- Screenshots liegen unter `/data/screenshots/<yyyy>/<mm>/<uuid>.png`, Pfade nie aus Eingaben.
- Kommentare werden escaped gerendert, Links bekommen `rel="noopener"`.
- Die Extension beantwortet Capture-Anfragen nur nach Nutzergeste (§8).
- Inhalte des Overlays laufen im Shadow DOM, aber im Kontext der Seite: Eine bösartige Seite könnte
  den Overlay-Token aus `localStorage` lesen. Akzeptiertes Restrisiko, weil nur unsere eigenen
  Teststände das Script einbinden; Tokens sind widerrufbar und auf 30 Tage begrenzt.

## 17. Reihenfolge der Umsetzung

1. Repo-Gerüst, Shared-Typen, Server mit DB, OIDC, Session, Gerätecode, Tokens, API. Inbox
   mit Sites, Liste, Detail, Tokens, Device. Docker-Image, Compose. → lokal nutzbar mit curl.
2. Overlay: Einbindung, Login, Pin-Modus, Anker, DOM-Fallback-Screenshot, Panel, Polling.
3. Extension und Protokoll, Release-Zip.
4. CLI und Skill.
5. kube-Chart, OAuth-Client, erster Prod-Rollout, Extension im Team verteilen.

## 19. Bewusst offen gelassen (Review 2026-10-11)

Zwei Findings der unabhängigen Review wurden geprüft und absichtlich nicht umgesetzt:

- **Anker bleiben bei Textabweichung am strukturellen Treffer.** Wird ein Listeneintrag
  gelöscht, kann sein Pin auf den Nachfolger an derselben Position wandern, statt als verwaist
  zu gelten. Die Alternative, strukturelle Treffer bei abweichendem Text zu verwerfen, würde
  jede Copy-Änderung („Speichern“ statt „Save“) zum Pin-Verlust machen. Die Vorschau im
  Thread zeigt den ursprünglichen Screenshot, der Fall ist dort erkennbar.
- **Screenshots bleiben optional.** Scheitert die Aufnahme (kein Extension, DOM-Fallback
  blockiert), darf trotzdem gesendet werden. Ein Kommentar ohne Bild ist nützlicher als kein
  Kommentar; der Reporter sieht vor dem Senden, dass kein Bild angehängt ist.
